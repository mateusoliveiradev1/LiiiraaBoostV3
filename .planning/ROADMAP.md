# Roadmap: Liiiraa Boost

## Overview

Liiiraa Boost will move from a single truthful product contract to a complete desktop experience, then a complete web experience, and only then connect the real commercial control plane and Windows optimization engine. Each phase closes an observable capability while preserving the chosen horizontal sequence: visual and UX quality is established before privileged behavior, scenario adapters are never presented as real machine data, and every later integration must satisfy the same generated contracts already exercised by the finished interfaces.

## Phases

- [x] **Phase 1: Product Truth and Modular Contracts** - Establish the versioned, truthful, enforceable foundation shared by every surface and future adapter. (completed 2026-07-27)
- [x] **Phase 2: Complete Desktop Experience** - Deliver the installable, bespoke, fully navigable desktop UX contract with every planned state represented honestly. (completed 2026-07-30)
- [ ] **Phase 3: Complete Web Experience** - Deliver the public site, documentation, download path, account shell, and isolated admin shell as one coherent web experience. (visual gap closure planned)
- [ ] **Phase 4: Identity, Commerce, Devices, and Administration** - Connect secure accounts, subscriptions, device licensing, support, and governed administration end to end.
- [ ] **Phase 5: Hardware Intelligence and Measured Evidence** - Replace diagnostic scenarios with capability-driven Windows inventory and defensible before/after evidence.
- [ ] **Phase 6: Transactional Plans and Recovery** - Let users approve, apply, verify, and safely reverse personalized plans through a hardened privilege boundary.
- [ ] **Phase 7: Verified Optimization Catalog** - Ship hardware-gated optimization families whose safety and benefit are proven before promotion.
- [ ] **Phase 8: Game Profiles and Session Automation** - Discover games and apply the same safe profile lifecycle whether they start inside or outside Liiiraa Boost.
- [ ] **Phase 9: Advisory AI and Secure Support** - Add consent-bound conversational guidance and support packages without granting AI execution authority.
- [ ] **Phase 10: Trusted Distribution and Production Operations** - Deliver signed channels, declarative profiles, release provenance, observability, and production release gates.

### Phase 2: Complete Desktop Experience

**Goal**: Users can install and traverse a finished, distinctive Liiiraa Boost desktop experience that represents the complete product surface and every critical state without claiming simulated optimization as real.

**Depends on**: Phase 1

**Requirements**: UX-01, UX-02, UX-03, UX-04, UX-05, UX-06, UX-07, UX-08, UX-09, UX-10, UX-11, UX-12

**Success Criteria** (what must be TRUE):

1. User can install and open the signed, non-elevated Tauri app and complete a guided calibration covering inventory, diagnosis, restore readiness, goals, and priority games.
2. User sees a contextual home centered on the next recommended action, selected game profile, and current system state, then navigates by goal into component-level detail.
3. User can use the global command center, pin controlled favorites, and review prioritized activity without turning the product into a crowded generic dashboard.
4. Every planned module has deliberate loading, empty, offline, permission, unsupported, partial-failure, restart-pending, recovery, and expired-entitlement behavior with no dead controls or unlabeled fixture values.
5. User can complete every desktop flow in PT-BR or English with keyboard and assistive technology, scaled UI, reduced motion, WCAG 2.2 AA contrast, and status meaning that never relies on color alone.

### Phase 4: Identity, Commerce, Devices, and Administration

**Goal**: Users can securely operate a real subscription account and one-device license while authorized staff work only through isolated, consent-bound, auditable administration.

**Depends on**: Phase 3

**Requirements**: WEB-04, WEB-05, WEB-06, WEB-07, IDEN-01, IDEN-02, IDEN-03, IDEN-04, IDEN-05, IDEN-06, IDEN-07, IDEN-08, IDEN-09

**Success Criteria** (what must be TRUE):

1. User can authenticate with verified email, supported social providers, or passkeys, enable MFA, and recover access through security-reviewed flows; administrators face stronger authentication for critical actions.
2. User can manage profile, security methods, subscription, invoices, support requests, and exactly one active PC from the account application.
3. User can revoke a privacy-preserving device identity and bind a replacement after the 30-day cooldown, while Premium remains cryptographically verifiable for seven offline days.
4. Expiration blocks new paid actions but leaves existing changes intact and keeps diagnostic history, security warnings, and restoration available.
5. Delayed or duplicate payment events cannot corrupt entitlement state, and staff can access user-provided diagnostics only through role-specific, time-limited consent that creates an immutable audit event.

### Phase 5: Hardware Intelligence and Measured Evidence

**Goal**: Users can see what their actual PC supports and compare only trustworthy, resource-bounded measurements whose provenance and limitations are explicit.

**Depends on**: Phase 4

**Requirements**: DIAG-01, DIAG-02, DIAG-03, DIAG-04, DIAG-05, DIAG-06, DIAG-07, MEAS-01, MEAS-02, MEAS-03, MEAS-04, MEAS-05, MEAS-06

**Success Criteria** (what must be TRUE):

1. User can inventory CPU, GPU, memory, storage, network, display, audio, USB, Windows build, drivers, security state, and installed games, with Windows 11, Windows 10 LTSC/ESU, and unsupported consumer Windows 10 states distinguished.
2. User can see evidence freshness and the exact reason an operation is compatible, unsupported, hidden, or Experimental; unknown, stale, contradictory, or unavailable evidence fails closed.
3. User can capture a documented system baseline and reliable supported game-session metrics including methodology, timestamp, environment identity, quality, and collector overhead.
4. The product rejects invalid before/after comparisons, exposes uncertainty or degraded coverage, and never substitutes estimates for unavailable evidence.
5. User can compare accepted sessions through a summary, detailed diff, timeline, and exportable report while collection stays within budget and reduces sampling during active games.

### Phase 6: Transactional Plans and Recovery

**Goal**: Users can approve and execute personalized optimization plans with proportional risk controls, exact prior-state journaling, outcome verification, and dependable recovery.

**Depends on**: Phase 5

**Requirements**: PLAN-01, PLAN-02, PLAN-03, PLAN-04, PLAN-05, PLAN-06, PLAN-07, PLAN-08

**Success Criteria** (what must be TRUE):

1. User can generate a plan from goals, capabilities, and current evidence, then add, remove, and inspect every operation before approval.
2. Every operation exposes purpose, expected impact, risk, evidence, compatibility, restart effect, previous value, and recovery method under the selected Verificado, Avançado, Experimental, or Extremo policy.
3. High-risk work cannot proceed until proportional explanation, authentication, recovery preparation, and confirmation are complete, and every side effect is journaled and verified.
4. User can restore one operation, a complete plan, or a recovery checkpoint after failure or reboot; partial failure pauses safely, rolls back only the necessary dependency set, explains the cause, and preserves an auditable diagnostic.

### Phase 10: Trusted Distribution and Production Operations

**Goal**: Users receive only verifiable application and profile releases, while production operation remains observable, privacy-bounded, resource-efficient, and automatically blocked when critical quality gates fail.

**Depends on**: Phase 9

**Requirements**: RELS-01, RELS-02, RELS-03, RELS-04, RELS-05, RELS-06, RELS-07

**Success Criteria** (what must be TRUE):

1. User receives only signed Stable, Beta, or Experimental application updates from the selected channel, with application and profile updates using separate identities and revocation paths.
2. Downloaded profiles verify as signed declarative data and can reference only operations already compiled into the installed engine.
3. Every releasable artifact includes an SBOM, provenance, signature verification, staged rollout, health monitoring, and a tested rollback path.
4. The background Windows service stays within agreed idle CPU and memory budgets on the supported hardware matrix.
5. Production emits privacy-bounded OpenTelemetry signals and cannot deploy until specification, type, unit, property, contract, migration, security, accessibility, visual, recovery, and end-to-end gates pass.

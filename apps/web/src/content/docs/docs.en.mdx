# Liiiraa Boost documentation

This reviewed repository corpus mirrors the admitted documentation records used by the public application. Each document keeps the same task order: purpose, next action, evidence, risks, compatibility, recovery, and technical detail.

## Getting started

### Purpose

Understand where each task happens before following product guidance. The website explains preparation, measurement, optimization review, restoration, privacy, and updates; Windows changes happen only inside the desktop application after review.

### Next action

Confirm that the desktop app reports the `current` documentation version and `stable` channel, then continue to Prepare a session.

### Evidence

Use the visible version, channel, review date, owner, and validation state to confirm that this guidance belongs to the current release context.

### Risks

Do not treat product examples or interface captures as measured performance evidence from your own PC.

### Compatibility

This guidance covers supported Windows 10 and Windows 11 desktop compositions. Hardware-specific support remains subject to the compatibility record.

### Recovery

If the version or locale does not match, keep this page open and choose the explicit compatible alternative. No content is silently substituted.

### Technical detail

Contextual links are resolved from locale, version, channel, task slug, domain, and exact section anchor.

## Prepare a session

### Purpose

Prepare the game, dependencies, and recovery path before any future optimization operation.

### Next action

Close unrelated workloads, confirm the selected game, and review the preflight state without changing system configuration.

### Evidence

Record the selected game, detected constraints, declared goals, and available recovery baseline in the local activity view.

### Risks

An incomplete preflight can make later measurements incomparable. Stop when a dependency or recovery prerequisite is unavailable.

### Compatibility

Preparation applies to Windows 10 and Windows 11; individual games, anti-cheat systems, and devices may impose narrower boundaries.

### Recovery

Cancel the preparation flow to return to the last verified local state. No remote authority is required.

### Technical detail

The desktop preparation route family keeps game and session identifiers bounded and rejects unknown navigation parameters.

## Measure a baseline

### Purpose

Capture a comparable baseline before drawing a performance conclusion.

### Next action

Use the same workload, duration, collector coverage, and power context for baseline and comparison runs.

### Evidence

Inspect provenance, capture window, sample coverage, rejected comparisons, and collector overhead before accepting a result.

### Risks

Different workloads or degraded coverage can create a false improvement. A schema-valid record is not automatically a valid comparison.

### Compatibility

Measurement guidance applies to Windows 10 and Windows 11 when the selected collectors are available for the device.

### Recovery

Reject the comparison and return to the last accepted baseline when coverage, context, or provenance differs.

### Technical detail

`LB-COLLECTOR`, `WIN11-24H2`, and evidence receipt identifiers remain searchable as complete technical tokens and as component terms.

## Review an optimization

### Purpose

Review proposed effects, evidence, risk, and rollback before a future operation can be authorized.

### Next action

Compare the proposed plan with the current baseline and confirm every consequence and recovery step.

### Evidence

Each operation must identify its source, scope, applicable version, validation state, and what remains unproven.

### Risks

Do not infer a guaranteed gain from a recommendation. Compatibility and measurable benefit depend on the exact hardware and workload.

### Compatibility

Only operations explicitly supported for the detected Windows version and device state are eligible for later execution.

### Recovery

Keep the snapshot and inverse operation visible before confirmation. Stop if either is missing.

### Technical detail

The website can explain a plan, but only the desktop application can apply a reviewed operation. If the required evidence or recovery path is missing, the operation remains blocked.

## Restore a plan

### Purpose

Return a reviewed plan to its last verified state using the recorded recovery path.

### Next action

Select the exact plan receipt, inspect its snapshot and inverse operations, and verify that the target state matches the receipt.

### Evidence

Use the immutable activity sequence, snapshot identity, plan identifier, and post-restore verification result.

### Risks

Restoring the wrong plan or an incompatible snapshot can create a partial state. Never choose a recovery record by title alone.

### Compatibility

Recovery is valid only for the device, application version, and operation set recorded by the original plan.

### Recovery

If verification cannot establish the expected state, stop, preserve the local evidence, and follow the escalation path.

### Technical detail

Plan and snapshot identifiers are exact, bounded values. A historical document can explain an old receipt but cannot authorize a current action.

## Diagnose LB-ERR:0x80070005

### Purpose

Diagnose an observed access-denied capture state without weakening Windows protections.

### Next action

Confirm the exact error code and affected source in the local activity record, then close any active capture before retrying safe verification.

### Evidence

Match `LB-ERR:0x80070005`, `ACL-WIN32`, the source identifier, timestamp, and redacted diagnostic receipt.

### Risks

Do not bypass access controls or security software. This guide does not provide a generic system-mutation recipe.

### Compatibility

The observed state may occur on Windows 10 or Windows 11; the available source and permission boundary can differ by build and policy.

### Recovery

Return to the previous verified capture source. If the state remains, export the redacted receipt and escalate to support.

### Technical detail

The resolver indexes the full error code and identifier punctuation so the exact observed state remains distinguishable.
